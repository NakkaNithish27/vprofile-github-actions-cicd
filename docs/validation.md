# Validation

[← Back to README](../README.md)

## 1. Validation Overview

This document defines how the VProfile GitHub Actions CI/CD pipeline should be validated from source change through container image publication.

The validation path is:

```text
GitHub
   ↓
GitHub Actions
   ↓
Build
   ↓
Testing
   ↓
Security Scan
   ↓
Publishing Gate
   ↓
Docker Build
   ↓
Amazon ECR
```

The final workflow uses four major jobs:

1. `Build`
2. `Testing`
3. `Security_Scan`
4. `BUILD_AND_PUBLISH`

The validation strategy does not treat a single green workflow status as sufficient evidence.

Each major capability should have a corresponding validation point and, where appropriate, high-signal evidence.

---

# 2. Validation Philosophy

The validation model follows:

```text
Capability
    ↓
Validation Method
    ↓
Expected Result
    ↓
Evidence
    ↓
Claim Boundary
```

For example:

```text
Docker Image Publication
        ↓
Inspect Amazon ECR
        ↓
Expected image/tag exists
        ↓
ECR evidence
        ↓
Proves image publication
```

This distinction is important:

> A successful workflow stage proves that the configured stage completed successfully. It does not automatically prove every external system state or production outcome.

---

# 3. Validation Levels

The project is validated at four practical levels:

```text
Level 1 — Workflow Execution
        ↓
Level 2 — Individual Job / Artifact Results
        ↓
Level 3 — External Registry State
        ↓
Level 4 — Evidence and Claim Verification
```

Each level answers a different question.

---

## Level 1 — Workflow Execution

Confirm that GitHub Actions executes the expected job dependency graph.

Expected topology:

```text
             ┌──► Testing ────────┐
Build ───────┤                    ├──► BUILD_AND_PUBLISH
             └──► Security_Scan ──┘
```

The source material specifically describes:

```text
Build
  ↓
Testing + Security_Scan
```

with Testing and Security Scan starting after Build completes and running independently.

---

## Level 2 — Individual Job and Artifact Results

Validate the outputs generated by the individual jobs.

Expected outputs include:

```text
Build
  └── vprofile-app

Security_Scan
  └── trivy-scan-results
```

The workflow artifacts are important because GitHub-hosted runners are ephemeral.

The build WAR is persisted as `vprofile-app`, while the Trivy JSON result is persisted as `trivy-scan-results`.

---

## Level 3 — External Registry State

The publishing job should be validated outside the GitHub Actions runner.

Expected external state:

```text
Amazon ECR
    │
    └── Docker image
          │
          └── commit-SHA tag
```

The ECR repository should be checked after the workflow completes and the image should exist with the expected commit SHA tag.

---

## Level 4 — Evidence and Claim Verification

The final validation step is to determine whether the available evidence actually supports the project claims.

The project should distinguish:

```text
Course Material
      ↓
Defines the capability demonstrated by the practical
```

from:

```text
Personal Environment Evidence
      ↓
Proves personal execution
```

Course screenshots or course material must not be presented as evidence of personal execution.

---

# 4. Validation Matrix

| Capability | Validation Method | Expected Result | Evidence |
|---|---|---|---|
| GitHub Actions workflow | Execute workflow | Workflow starts successfully | Workflow run |
| Build job | Inspect Build job | Maven build succeeds | Build logs |
| WAR generation | Inspect Build artifact | `vprofile-app` exists | Artifact listing |
| Testing job | Inspect Testing job | Tests complete successfully | Testing logs |
| Checkstyle | Inspect Testing output | Checkstyle executes successfully | Testing logs |
| Security Scan | Inspect Security_Scan job | Trivy executes | Security Scan logs |
| Trivy result | Inspect artifacts | `trivy-scan-results` exists | Artifact listing |
| Trivy JSON | Download artifact | JSON result available | Downloaded result |
| Job parallelism | Inspect workflow graph | Testing and Security Scan follow Build independently | Workflow graph |
| Publishing gate | Inspect job dependencies | Publish waits for Build, Testing, Security_Scan | Workflow graph |
| Main-branch condition | Run workflow from non-main reference | Publishing job is skipped | Workflow run |
| Docker build | Inspect publishing logs | Docker image builds successfully | `BUILD_AND_PUBLISH` logs |
| ECR authentication | Inspect publishing logs | ECR login succeeds | Publishing logs |
| ECR publication | Inspect ECR | Image exists | ECR evidence |
| Image identity | Compare image tag and Git revision | SHA matches | Git + ECR evidence |

---

# 5. Build Validation

The Build job is the first validation stage.

Expected flow:

```text
Checkout
   ↓
Maven Build
   ↓
WAR Artifact
```

The build should complete successfully.

The expected Maven output is a generated WAR file under:

```text
target/*.war
```

The workflow persists the artifact as:

```text
vprofile-app
```

### What this proves

A successful Build job demonstrates that:

- the repository can be checked out
- Maven can execute in the GitHub Actions environment
- the application workload can be built
- the expected WAR artifact is generated

### What this does not prove

It does not prove:

- production application correctness
- production performance
- production availability
- successful deployment
- business-level functionality beyond the tests that actually execute

---

# 6. Testing Validation

The Testing job depends on Build:

```yaml
needs: Build
```

The validation sequence is:

```text
Build
  ↓
Maven Test
  ↓
Checkstyle
```

The Testing job should complete successfully.

### What this proves

A successful Testing job demonstrates that the configured Maven tests and Checkstyle stage completed successfully.

### What this does not prove

A passing test stage does not establish:

- complete application test coverage
- production correctness
- absence of all defects
- absence of security vulnerabilities

Testing is one validation layer, not a complete guarantee of application quality.

---

# 7. Security Scan Validation

The Security Scan job depends on Build:

```yaml
needs: Build
```

The configured Trivy scan uses:

```yaml
scan-type: fs
scan-ref: .
format: json
exit-code: 0
output: trivy-results.json
```

The scan is a filesystem scan of the checked-out repository that produces a JSON result.

The expected flow is:

```text
Repository
    ↓
Trivy
    ↓
trivy-results.json
    ↓
Upload Artifact
    ↓
trivy-scan-results
```

---

# 8. Trivy Result Validation

After the workflow completes, the GitHub Actions run should contain:

```text
vprofile-app
trivy-scan-results
```

The Trivy result can be downloaded from the workflow's artifact section.

The downloaded result contains the JSON scan output.

The JSON can contain structured vulnerability information such as:

- vulnerability identifiers
- severity
- affected packages
- affected versions

### What this proves

It proves that:

- Trivy executed
- the repository filesystem was scanned
- a machine-readable result was generated
- the result was persisted as a workflow artifact

### Important boundary

The current configuration uses:

```yaml
exit-code: 0
```

Therefore the scan is **informational rather than blocking**.

The current behavior is:

```text
Scan
 ↓
Report
 ↓
Continue
```

rather than:

```text
Scan
 ↓
Vulnerability Found
 ↓
Pipeline Blocked
```

Therefore:

> A successful Security Scan job must not be described as proof that the repository contains no vulnerabilities.

---

# 9. Parallel Job Validation

The intended topology is:

```text
             ┌──► Testing
Build ───────┤
             └──► Security_Scan
```

Testing and Security Scan both depend on Build but not on each other.

### Validation method

Open the workflow run and inspect the job graph.

### Expected result

```text
Build
  ↓
Testing
Security_Scan
```

Both downstream validation jobs should be independent of each other.

### What this proves

It demonstrates that the workflow correctly expresses the intended job dependencies rather than unnecessarily serializing independent validation work.

---

# 10. Publishing Gate Validation

The final job declares:

```yaml
needs: [Build, Testing, Security_Scan]
```

This creates the final fan-in:

```text
Build
  +
Testing
  +
Security_Scan
       ↓
BUILD_AND_PUBLISH
```

### Validation method

Inspect the GitHub Actions job graph and `BUILD_AND_PUBLISH` job status.

### Expected result

The publishing job should execute only after the required validation jobs complete successfully.

### What this proves

It demonstrates that the workflow has an explicit validation-to-publishing boundary.

---

# 11. Main-Branch Publishing Validation

The publishing job uses:

```yaml
if: github.ref == 'refs/heads/main'
```

The expected behavior is:

```text
Pull Request / Other Reference
        ↓
Workflow runs
        ↓
BUILD_AND_PUBLISH
        ↓
SKIPPED
```

while:

```text
Push to main
        ↓
Workflow runs
        ↓
BUILD_AND_PUBLISH
        ↓
RUNS
```

This demonstrates that:

```text
Workflow trigger
       ≠
Publishing authorization
```

---

# 12. Docker Build Validation

The `BUILD_AND_PUBLISH` job builds the Docker image from the repository source.

The expected sequence is:

```text
Checkout
   ↓
AWS Authentication
   ↓
ECR Login
   ↓
Docker Build
   ↓
Docker Push
```

The Docker build should complete successfully.

### What this proves

A successful Docker build demonstrates that the configured Dockerfile and build context can produce a container image in the GitHub Actions environment.

### What this does not prove

It does not by itself prove that:

- the application is running correctly in production
- the container is deployed
- the container is highly available
- runtime behavior is correct under production traffic

---

# 13. ECR Authentication Validation

The publishing job configures AWS credentials and then performs ECR login.

The authentication chain is:

```text
GitHub Environment
       ↓
AWS Credentials
       ↓
Configure AWS Credentials
       ↓
ECR Login
       ↓
Docker Push
```

### Validation method

Inspect the `BUILD_AND_PUBLISH` logs.

### Expected result

The AWS credential configuration and ECR login steps complete successfully.

### What this proves

It demonstrates that the workflow can authenticate to the configured AWS account and ECR registry using the configured credentials.

It does not prove that the credentials are appropriate for a production-grade identity architecture.

---

# 14. ECR Image Validation

After `BUILD_AND_PUBLISH` completes, inspect the Amazon ECR repository.

Expected:

```text
Amazon ECR
    │
    └── vprofile application image
             │
             └── <commit-sha>
```

### What this proves

It demonstrates that the Docker image was successfully published to Amazon ECR.

### What this does not prove

It does not prove that the image has been deployed to a runtime platform.

The project ends at ECR.

---

# 15. Commit-SHA Traceability Validation

The Docker image uses:

```text
github.sha
```

as its image tag.

The intended relationship is:

```text
GitHub Commit
      │
      ▼
github.sha
      │
      ▼
Docker Image Tag
      │
      ▼
Amazon ECR
```

### Validation method

Compare:

```text
GitHub commit SHA
```

with:

```text
Amazon ECR image tag
```

### Expected result

They should match exactly.

### What this proves

It demonstrates source-to-container traceability:

```text
Source Revision
      ↕
Container Image
```

This is one of the highest-value validation points in the project.

# 16. End-to-End Validation

The complete successful flow is:

```text
GitHub
   ↓
Workflow Trigger
   ↓
Build ✓
   ↓
┌───────────────┐
│               │
▼               ▼
Testing ✓   Security_Scan ✓
│               │
└───────┬───────┘
        ▼
BUILD_AND_PUBLISH ✓
        │
        ▼
Docker Build ✓
        │
        ▼
ECR Push ✓
        │
        ▼
Image Exists ✓
        │
        ▼
Commit SHA Matches ✓
```

The recommended verification sequence is:

1. Actions tab — verify all four jobs are green
2. `BUILD_AND_PUBLISH` logs — verify each step
3. AWS ECR — verify the image exists with the commit SHA tag
4. GitHub commit page — verify the SHA matches the ECR tag
5. Optionally trigger the workflow manually using `workflow_dispatch` and verify another complete run

# 17. Evidence Strategy

Evidence should be **minimal and high-signal**.

The repository should not become a screenshot dump.

The evidence directory is:

```text
evidence/screenshots/
```

The preferred evidence categories for this project are:

```text
1. Successful GitHub Actions workflow
2. Workflow job/dependency graph
3. Build artifact
4. Trivy scan result
5. Amazon ECR image
6. Commit SHA traceability
```

These correspond directly to the project's major engineering claims.

# 19. Evidence Quality Rules

Every screenshot added to the repository should satisfy at least one of these conditions.

### Rule 1 — Proves a Major Capability

Example:

```text
ECR image exists
```

### Rule 2 — Proves an Important Integration

Example:

```text
GitHub Actions → Amazon ECR
```

### Rule 3 — Proves an Important Control

Example:

```text
BUILD_AND_PUBLISH gated by needs
```

### Rule 4 — Supports an Interview Discussion

Example:

```text
Commit SHA → ECR image tag
```

Avoid screenshots that merely show:

- generic GitHub pages
- empty repositories
- generic AWS console pages
- plugin/action search results
- course slides
- course screenshots
- unrelated configuration screens

The evidence should communicate an engineering result, not simply demonstrate that a page exists.

---

# 20. Personal Evidence Boundary

The learning material establishes what the practical demonstrates.

It does not, by itself, prove personal execution.

Therefore:

```text
Course Material
      ↓
Defines Capability
```

while:

```text
Personal Environment
      ↓
Execution Evidence
```

Only screenshots or outputs from the completed personal environment should be presented as proof of personal execution.

Course screenshots must not be presented as personal evidence.

This boundary is particularly important for a portfolio repository because the repository should distinguish between:

```text
What the practical teaches
```

and:

```text
What I personally configured, executed, and validated
```

# 21. Validation Claims

The following claims are appropriate **when the corresponding validation has actually been completed**:

### GitHub Actions

> GitHub Actions successfully orchestrated the configured CI/CD workflow.

### Maven

> The workflow successfully built the application workload.

### Testing

> The configured Maven tests and Checkstyle validation executed successfully.

### Security

> Trivy was integrated as a filesystem security scan and its JSON result was persisted as a workflow artifact.

### Docker

> The workflow successfully built the application container image.

### Amazon ECR

> The workflow successfully published the Docker image to Amazon ECR.

### Traceability

> The published ECR image was tagged with the Git commit SHA corresponding to the source revision.

These should only be claimed as completed results when the corresponding personal execution and evidence exist.

---

# 22. Validation Boundaries

Successful validation of this project does **not** establish:

- production-scale reliability
- high availability
- disaster recovery
- zero-downtime deployment
- automated rollback
- Kubernetes deployment
- ECS deployment
- infrastructure provisioning through Terraform
- production observability
- enterprise-grade AWS identity federation
- complete vulnerability policy enforcement
- application correctness beyond the tests actually executed

The current architecture ends at:

```text
Docker Image
     ↓
Amazon ECR
```

It does not continue into:

```text
Amazon ECR
     ↓
Runtime Platform
     ↓
Running Application
```

---

# 23. Important Security Validation Boundary

The Trivy scan is currently configured with:

```yaml
exit-code: 0
```

Therefore:

```text
Vulnerability Found
        ↓
Report Generated
        ↓
Pipeline Continues
```

The validation should therefore report:

> **Trivy scan executed successfully and produced a vulnerability report.**

It should **not** report:

> **The application passed security scanning with no vulnerabilities.**

The latter claim is unsupported by the current configuration and by the fact that the scan is informational rather than blocking.

Before considering the project validated, confirm:

### Workflow

- [ ] GitHub Actions workflow starts successfully
- [ ] Expected workflow trigger is observed
- [ ] `Build` executes successfully
- [ ] `Testing` executes successfully
- [ ] `Security_Scan` executes successfully
- [ ] `BUILD_AND_PUBLISH` executes successfully on `main`

### Job Topology

- [ ] Testing depends on Build
- [ ] Security_Scan depends on Build
- [ ] Testing and Security_Scan execute independently
- [ ] BUILD_AND_PUBLISH depends on all three upstream jobs

### Build

- [ ] Maven build succeeds
- [ ] WAR artifact is produced
- [ ] `vprofile-app` artifact is available

### Testing

- [ ] Maven tests execute
- [ ] Checkstyle executes
- [ ] Testing job completes successfully

### Security

- [ ] Trivy executes
- [ ] Filesystem scan is performed
- [ ] JSON result is generated

### Publishing

- [ ] AWS credentials are resolved from the configured environment
- [ ] ECR login succeeds
- [ ] Docker build succeeds
- [ ] Docker image is tagged with the commit SHA
- [ ] Docker push succeeds

### ECR

- [ ] Expected ECR repository is accessible
- [ ] Image exists
- [ ] Image tag matches the Git commit SHA

### Evidence

- [ ] Successful workflow evidence captured
- [ ] Job graph evidence captured if useful
- [ ] Build artifact evidence captured if useful
- [ ] Trivy artifact evidence captured if useful
- [ ] ECR image evidence captured
- [ ] Git SHA / ECR tag traceability evidence captured
- [ ] Only personal execution evidence is labeled as such

```text
        VALIDATE

           ▼
     ┌─────────────┐
     │    Build    │
     └──────┬──────┘
            │
      ┌─────┴─────┐
      ▼           ▼
   Testing     Security
      │           │
      └─────┬─────┘
            ▼
       Publish Gate
            │
            ▼
       Docker Image
            │
            ▼
```

The central validation principle is:

> **Do not validate only that the workflow is green. Validate the outputs, external state, traceability, and evidence that support the specific engineering claims being made.**

That produces a portfolio project whose claims are not merely documented, but tied to observable validation points and defensible evidence.
